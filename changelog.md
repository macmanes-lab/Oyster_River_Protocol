### CHANGELOG

ORP Version 4.0.0 <- 3.1.0

**The assembly this pipeline produces changes in this release.** The new scorer computes the four score components, the contig score and the assembly score from the same formulas as the Ruby, but its inputs changed, so contig scores move and -- more importantly -- reorder. `makeorthout` keeps the highest-scoring member of each orthogroup, so that reordering reaches the assembled `.ORP.fasta` itself, not just the reported number: 14.5-19% of contig pairs order oppositely across the boundary. The `TRANSRATE SCORE` lines in `reports/qualreport.<run>` are not comparable to any earlier ORP release's, and the `transrate` entry in `sampledata/benchmarks.md` needs a fresh baseline. pytransrate's `scripts/compare_orthogroup_picks.py` measures exactly which orthogroups change representative between two runs.

- replace the bundled Ruby `orp-transrate` with [pytransrate](https://github.com/macmanes-lab/pytransrate) 2.0.0, pip-installed into the `orp` env off its pinned `v2.0.0` tag. The Ruby version is pinned to Ruby 2.2.0 (EOL since 2018), ships as an x86_64-linux-only 30MB bundle, and depends on three abandoned binaries; none of that could be carried forward. The CLI is drop-in (`-a`/`-o`/`-t`/`--left`/`--right` unchanged) and the CSV column order is preserved deliberately, so `reportgen`'s positional reads at indices 36/37 of `assemblies.csv` and `scripts/pick_best_contigs.py`'s column 9 of `contigs.csv` are untouched. **Scores are not comparable across this boundary and are not meant to be**: snap-aligner 1.0dev.96 -> 2.0.5 introduced soft clipping, and the old `bam-read` helper advanced its reference cursor over soft-clipped bases as though they consumed reference, shifting a clipped read's coverage contribution rightward -- inert under an aligner that never clipped, corrupting under one that does. Coverage now follows the SAM spec and agrees with `samtools depth`. Measured across three assemblies of one library: `bases_uncovered` rises 3.1-4.5x and the assembly score drops 0.008-0.070, while the good-mapping *rate* is unchanged to +/-0.001 -- the two implementations agree about the reads and disagree about the contigs. Because `makeorthout` keeps the highest-scoring member of each orthogroup, it is contig-score *ordering* and not level that reaches the assembly: 14.5-19% of contig pairs order oppositely, so the final `.ORP.fasta` will differ. pytransrate ships `scripts/compare_orthogroup_picks.py` to measure exactly which orthogroups change representative. The `transrate` entry in `sampledata/benchmarks.md` needs a fresh baseline for the same reason. Install-side this retires the tarball, its `make` target, the Dockerfile `ENV`/`.profile` PATH entries, and INSTALL.md steps 5 and 8 -- a console script inside the env needs none of them. `check()` gains `snap-aligner`, which pytransrate shells out to, so a missing one fails in preflight instead of hours in at `orthotransrate`
- upgrade salmon 2.5.1 -> 2.7.0 in the `orp` env (and add `snap-aligner=2.0.5`/`pysam` for pytransrate, which targets 2.7.0 -- so one env serves both rather than needing a separate `orp_transrate`). Every flag ORP passes was checked against the 2.x migration notes first and nothing breaks: `salmon index` keeps `-t`/`-i`/`-k`/`--threads`, `salmon quant` keeps `-p`/`-i`/`--seqBias`/`--gcBias`/`--libType`/`-1`/`-2`/`-o`, and `quant.sf`'s columns are unchanged so `filter_tpm` still reads TPM from column 4. Dropped `--validateMappings`, which 2.x ignores now that selective alignment is the default -- it was a no-op that read as though it still switched something on. Kept `--no-version-check`, also a no-op, since it stays meaningful against a 1.x salmon. The behavioral change is 2.6.0 making deterministic quantification the default, which lands entirely in the 2.5.1 -> 2.6.0 step (2.7.0 is byte-identical to 2.6.0): TPMs move, and the salmon step stops being a source of run-to-run drift. Downstream this is inert at the default `--tpm-filt 0`, where `filter_tpm` writes the LOWEXP list only when `tpm < 0` and so leaves it empty and `secondfilter` copying through unchanged; only `--tpm-filt > 0` runs see membership shift near the threshold. `orp_trinity`'s own `salmon=1.10.3` is a separate env and is untouched
- fix a resumability hole the salmon upgrade exposed: 2.7.0 requires index format v2 and rejects any index an earlier salmon built, but `needs_run()` only ever compares mtimes -- so resuming a run started under 2.5.1 kept the stale `<run>.ortho.idx`, skipped `salmon_index`, and left `salmon quant` to fail against an index it could not read, once per retry. `stamp_tool_version()` now records the salmon version in `quants/salmon.version` and declares that file as an *input* to `salmon_index`, so a version change reads as an ordinary out-of-date input rather than a special case; the stamp is rewritten only when the version actually changes, or a rebuild would fire every run. `salmon_index` also clears the index directory before rebuilding, since a rebuild here is usually a rebuild over an index salmon has already refused
- clear the output directory before each of `orthotransrate()`/`transrate()`. pytransrate refuses an output directory that already holds an `assemblies.csv` rather than silently overwriting it the way the Ruby did, and `needs_run()` re-runs either step whenever the corrected reads are newer than that csv -- not only when it is absent -- so a resumed run would abort in preflight instead of rescoring. The `rglob("*.bam")` cleanup loops go at the same time: pytransrate deletes its own BAM on success unless `--keep-bam` is passed
- reclaim intermediate files instead of leaving a finished run's whole working tree on disk. A completed run now keeps `reports/`, `assemblies/<run>.ORP.fasta`, the four individual assemblies and the corrected read pair -- the last two gzipped -- and removes everything else: the trimmed-but-uncorrected reads, `orthofuse/` (OrthoFinder's all-vs-all output plus pytransrate's scoring of the pooled fasta, normally the largest directory in a run), `quants/`, `assemblies/diamond/`, `assemblies/working/`, and the chain of working assemblies between `orthofusing` and `.ORP.fasta`. All of it is reproducible from what's kept, and every number any of it contributed is already in `reports/qualreport.<run>`. `reports/<run>.cleanup.done` records what was kept and what was removed, with sizes. `--keep-intermediates` turns the whole thing off for debugging a run
- do the gzipping in the background, starting when each file is finished being *written* rather than when the pipeline is finished *reading* it -- which is much later, since the corrected reads feed every assembler and every alignment step through to `strandeval`, and the four assemblies are read again at `run_filtershort`, `diamond_*` and `posthack`. `compress_async()` queues the corrected pair the moment `run_rcorrector` returns and each assembly the moment its assembler returns, on a two-worker pool, so the compression runs alongside an assembler and `cleanup` at the end has nothing to do but unlink. A file whose background gzip failed or didn't finish is kept uncompressed rather than deleted, and `finish_compression()` joins the pool on every exit path including failure, so a run that dies mid-stage doesn't sit at interpreter exit with no explanation. Adds `pigz=2.8` to the `orp` env for this, with a plain-`gzip` fallback so an env built before it keeps working: a corrected read pair is tens of GB and single-threaded gzip can still be running long after the stage that was meant to hide it has ended
- delete the four `rcorr/<run>.TRIM_*.fastq` inline right after `run_rcorrector` rather than waiting for the end-of-run cleanup. They're the size of the raw input, nothing past read correction ever opens them again, and this is the earliest reclaim the pipeline has -- it frees roughly the corrected pair's own footprint before the assemblers start. `run_trimmomatic` declares a new `rcorr/<run>.trim.done` sentinel as its output in place of the TRIM files whenever the corrected pair is present and current, so a resumed run doesn't read their absence as a reason to re-trim; a working directory from before the sentinel existed still has its TRIM files and skips exactly as it always did
- add `already_complete()`, without which the cleanup above would turn a harmless re-invocation into a destructive one. `needs_run()` decides every step purely from whether its outputs exist and are current, so once cleanup has removed most of them, re-running `oyster.py` on a finished run directory -- a resubmitted cluster job, say -- would find nearly every stage out of date and silently reassemble from scratch over a completed run, where today it no-ops. `main()` now short-circuits on `reports/<run>.cleanup.done` plus an `.ORP.fasta` still newer than the raw reads, printing where the assembly and reports are; it returns before `timing_init()`, which would otherwise truncate the finished run's timing log on the way past. Deleting the marker forces a full re-run in place
- stop creating the `reads/` directory, which `setup()` has been making on every run since the port and which nothing has ever written to

ORP Version 3.1.0 <- 3.0.0

- split `run_trinity()` into `run_trinity_phase1()`/`run_trinity_phase2()` using Trinity's documented [multi-stage execution support](https://github.com/trinityrnaseq/trinityrnaseq/wiki/Running-Trinity#running-trinity-in-multiple-sequential-stages) (`--no_distributed_trinity_exec`, then a plain re-run that resumes from Phase 1's checkpoints); pair each phase with a different assembler instead of splitting one fixed lane for the whole run: Stage A runs Phase 1 alongside rnaSPAdes55/rnaSPAdes75 at `TRINITY_PHASE1_SHARE=0.25`, Stage B runs Phase 2 alongside Trans-ABySS at `TRINITY_PHASE2_SHARE=0.95`. Real-run evidence (`TIME2_SRR1789336_norm_py_5050parallel`, NOTES.md 2026-08-19) showed Phase 1 finishing in 90min regardless of its CPU share (confirming it's insensitive above Inchworm's own `--inchworm_cpu=10` cap), and Trans-ABySS's 4.5h runtime is ~3.2h single-threaded FASTQ read/graph-build that no CPU count can shrink (traced to `abyss-pe` falling through to the unthreaded `ABYSS` binary whenever neither Bloom-filter mode nor MPI is requested) -- so pairing Trans-ABySS with the dominant, highly-parallel Phase 2 instead of making Phase 2 wait for it reclaims most of what was previously idle Trinity-lane time, without risking SPAdes being starved of cores the way a single shared short-lane reservation would. Trans-ABySS's memory share is not cut along with its reduced CPU share, since its memory footprint doesn't shrink with core count the way SPAdes/Phase 1's do. Validated on a real run (`TIME2_SRR1789336_norm_py_955parallel`, `sampledata/benchmarks.md`): 37:06:19 TOTAL, beating both the no-split baseline (38:28:11, by 1h21m52s) and an even 50/50 split (42:28:36, by 5h22m17s)
- fix `strandeval()`'s `examine_strand.pl` call running bare `perl` instead of going through `conda run -n orp_trinity` like every other subprocess call in the file -- it inherited whatever `PATH` the oyster.py process itself had, and `examine_strand.pl`'s `SAM_reader.pm` shells out to `samtools`, which isn't on `PATH` at all once nothing is conda-activated (see the SLURM-script fix a couple of entries back in NOTES.md). Surfaced as `Can't exec "samtools": No such file or directory` on a real cluster run

ORP Version 3.0.0 <- 2.4.0

- replace oyster.mk (GNU Make) with oyster.py (Python 3.6+), the new primary pipeline entrypoint; every 2.4.0 fix and behavior below (software versions, BUSCO OrthoDB v12.2, NORMALIZE_READS, TPM/cd-hit/diamond-prerequisite fixes, etc.) carries forward unchanged except where noted here
- run independent stages concurrently, capped by the new `--max-parallel` flag (default 2, splitting `--cpu`/`--mem` across however many run at once): the 4 assemblers (Trinity/rnaSPAdes55/rnaSPAdes75/Trans-ABySS); the orthofuser vs. merge/orthotransrate branches; transrate vs. strandeval
- upgrade OrthoFinder 2.5.2 -> 3.1.5
- update software versions: Trinity 2.15.2, SPAdes 4.3.0, BUSCO 6.1.0, DIAMOND 2.2.5, salmon 2.5.1, samtools 1.24, bwa 0.7.19, rcorrector 1.0.7, cd-hit 4.8.1, trimmomatic 0.41, seqtk 1.5, mcl 22.282
- migrate BUSCO lineage database from OrthoDB v10 (eukaryota_odb10) to OrthoDB v12.2 (eukaryota_odb12.2), fetched via BUSCO's own `--download` instead of a hardcoded tarball URL
- update Python to 3.14 in orp_env.yml
- add [INSTALL.md](INSTALL.md): step-by-step install directions covering both the one-command `make` installer and the manual, environment-by-environment alternative, plus how to `mamba env update` an existing `orp` env and the known Python-3.14-solve gotchas above
- run the 4 assemblers as two fixed resource lanes instead of splitting `--cpu`/`--mem` evenly across all of them: Trinity gets its own lane with `TRINITY_LANE_SHARE` (80%) for the whole run, since it dominates wall-clock by orders of magnitude and its thread count is fixed once it launches (no way to hand it more CPU after the other three finish). The remaining 20% runs a second lane -- rnaSPAdes55, rnaSPAdes75, and Trans-ABySS in sequence -- firing each assembly's diamond search immediately after it finishes rather than waiting for the orthofuser/merge stage, which those particular diamond searches never actually depended on. Previously the even split meant Trinity ran alone at half `--cpu` for the last ~36 of its ~37 hours once the other three finished, with the other half of the machine idle
- add NORMALIZE_READS option to oyster.mk, exposing Trinity's `--no_normalize_reads` flag on the command line (defaults to FALSE, preserving prior behavior)


Minor/bugfix

- pin `python=3.14` for `orp_spades` specifically -- fixes SPAdes reporting "Python version 3.6.8 is not supported," a known SPAdes bug (ablab/spades#1319) where it detects a stray system Python instead of its own env's interpreter. Initially pinned across every environment for consistency, but reverted everywhere else after `orp_transabyss`'s solve failed (no non-RC Python 3.14 build available for that dependency set): each conda env's Python is fully isolated from every other env, so there's no real benefit to forcing the newest version outside the one env with an actual bug, and doing so just adds solver risk for older/less-actively-maintained packages
- add file-mtime-based resumability: a step whose output already exists and is newer than its inputs is skipped, so a failed/interrupted run can be re-invoked without recomputing finished work
- deliberately keep diamond, orp_diamond, salmon, and BUSCO sequential at full `--cpu` -- these are CPU-bound tools where splitting cores to enable overlap measured out to no net benefit (diamond) or a real regression (BUSCO, whose ~2 minutes dwarfs the ~13s of transrate+strandeval it would otherwise share cores with)
- add `--version` and full `argparse`-based `--help`
- retry a failed step up to twice (60s apart) before giving up, since a failure on a cluster is often transient (node preemption, filesystem hiccup) rather than a real bug; `run_spades()`/`run_transabyss()` also clean up their non-empty output dir before each retry, since both tools refuse to reuse one rather than resuming (Trinity is exempt from both, since it resumes from its own checkpoints in-place and its ~37h runtime means blindly retrying a deterministic failure could triple the wall time before giving up). Also log immediately when either of the two assembler-lane threads fails, rather than staying silent until the other lane -- often Trinity, tens of hours out -- separately finishes
- add `orp_orthofinder`/`orthofinder` to `check()`'s preflight tool verification, which never covered OrthoFinder before since it used to be a bare downloaded binary rather than a conda env
- remove the `orthofuser.py`-based version-check in the Makefile (`orthopath`/`orthufuserversion`, and the `orthofuser` target's curl/tar logic): dead code left over from ORP's pre-2021 install process, when a MacManes-lab-patched fork of OrthoFinder named `orthofuser.py` supplied nucleotide-input support that upstream OrthoFinder didn't have yet. That patch was retired in 2021 once upstream OrthoFinder added its own `-d` DNA-input flag, but the Makefile's check for it (a path that stopped existing at that point) was never cleaned up until now
- consolidate installed conda environments from 11 down to 5 (`orp`, `orp_spades`, `orp_trinity`, `orp_busco`, `orp_transabyss`) to make install faster and less failure-prone: `orp_rcorrector`, `orp_trimmomatic`, `orp_cdhit`, `orp_diamond`, and `orp_salmon` are folded into the base `orp` env, and `orp_sam` is removed entirely (its samtools was a version-for-version duplicate of `orp`'s, and its bwa/seqtk were never actually used from that env -- every bwa/seqtk call already ran inside `orp_trinity`). `orp_spades`/`orp_trinity`/`orp_busco`/`orp_transabyss` are left fully isolated since each has its own complex or fragile dependency tree -- `orp_trinity` in particular pins an old `salmon=1.10.3` for Trinity's internal isoform filtering, which must never resolve against the pipeline's own modern `salmon=2.5.1` now living in `orp`
- fix orthomerged diamond "unique gene count" rule listing spades55.diamond.txt as a prerequisite twice while omitting spades75.diamond.txt entirely
- fix readcheck's error path so a bad READ1/READ2 (missing file, too-short reads) actually reports its own error message when aborting the build, instead of failing on an unrelated "command not found"
- fix cd-hit-est's memory cap being hardcoded to 5000MB regardless of the run's requested MEM budget
- replace the list3->list5 diamond reconciliation step's shell loop (one grep per gene against the full diamond output) with a single hash-based Python pass, scripts/build_list5.py
- replace the per-orthogroup best-contig selection (one grep of contigs.csv per orthogroup via orthout.done) with a single hash-based Python pass, scripts/pick_best_contigs.py, retiring the orthout.done intermediate
- isolate all orp_* conda env creation from the user's/system's default conda channels
- pin a compatible salmon inside orp_trinity, since an unpinned resolve was picking a salmon 2.x whose Rust rewrite dropped flags Trinity's internal isoform filtering still calls with
- fix the TRANSRATE check to test the bundled binary directly instead of a stale proxy check
- remove dead RCORR/RCORRDIR/BUSCO/BUSCODIR/BUSCODB and TRINITY_KMER variables left over from earlier refactors
- blank out hardcoded /home/ubuntu paths in software/config.ini
- fix strandeval's `hist` histogram call: it was reading unfiltered raw data instead of the filtered numeric column, and separately losing its `-p '#'` argument when re-executed through conda run's internal shell
- fix the software-installed banner (SALMON/BUSCO/SPADES/etc.) printing between every timed step instead of once at the start, caused by per-step timing re-parsing the whole makefile
- fix the BUSCO score in qualreport picking up a line from BUSCO's JSON summary instead of its text summary, after newer BUSCO started writing both a .txt and .json short_summary per run
